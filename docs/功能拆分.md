# 功能拆分 —— 按数据所有权划分模块边界

> 本文档依据《开发文档》与《行文规范》，对系统进行功能拆分。
> **核心原则：以"数据所有权"划分模块（限界上下文），不按页面拆模块。**

---

## 1. 拆分原则

1. **一张表（一类数据）只有一个归属模块（Owner）**。谁拥有数据，谁负责它的增删改查与业务规则；其他模块只能"读引用"，不能直接改它的表。
2. **页面不是模块边界**。一个页面往往同时展示多个域的数据（例如成果详情页同时用成果、核查、评价三个域），页面只是数据的"组合视图"，不能因为有几个页面就切几个模块。
3. 模块之间通过 **外键 ID + 服务调用** 协作，禁止跨域直接操作对方的表、禁止把别的域的字段冗余进自己的表。
4. 共享能力下沉到**共享内核**（LLM、文件解析、存储、配置、安全、DB 基础设施），业务域依赖内核，内核绝不反向依赖业务域。
5. 依赖方向只允许"下游 → 上游"，不允许环依赖。

### 依赖方向总览

```
                         ┌──────────────────────────┐
                         │      共享内核 kernel       │
                         │ db / core(配置·安全)       │
                         │ llm / parsing / 文件存储   │
                         └────────────▲─────────────┘
        身份域 ──────────┐            │（所有业务域都可依赖内核）
        (User)           │            │
            ▲            │            │
   实训任务域 ────────────┤            │
   (TrainingTask)        │            │
            ▲            │            │
        成果域 ───────────┼────────────┘
   (Submission+文件)      │
          ┌──┴──┐         │
          ▼     ▼         │
       核查域  评价域       │   （核查/评价拥有各自结果，只读成果与任务）
 (Inspection) (Rubric/Score)
          └──┬──┘
             ▼
          报表域（Report）  —— 只读各业务域数据做聚合导出，不回写任何业务表
```

## 2. 数据所有权总表

| 数据 / 产物 | Owner 模块 | 后端模型 | 前端类型 |
| ---- | ---- | ---- | ---- |
| 用户、账号、角色 | 身份与用户域 | `User` | `User` |
| 实训任务、验收要求 | 实训任务域 | `TrainingTask` | `TrainingTask` |
| 成果提交记录、上传文件、解析结果 | 成果域 | `Submission`（+ `uploads/` 文件）| `Submission` |
| 智能核查结果 | 智能核查域 | `InspectionResult` | `InspectionResult` |
| 评价指标（量规） | 评价域 | `EvaluationRubric` | `Rubric` |
| 评分记录（AI 分 / 教师分）| 评价域 | `Score` | `Score`、`EvaluationResult` |
| 报表记录与导出文件 | 报表域 | `Report`（+ `reports/` 文件）| 报表历史项 |
| 模型调用、提示词 | 共享内核 | `services/llm/*` | —— |
| 文件解析能力 | 共享内核 | `services/parsing/*` | —— |
| 数据库/配置/安全/会话 | 共享内核 | `core/*`、`db/*` | `client.ts`、`store/auth.tsx` |

## 3. 各模块边界定义

### 模块 0：共享内核（kernel，无业务归属）

- **拥有**：数据库引擎与会话（`db/`）、配置（`core/config.py`）、密码与 JWT（`core/security.py`）、LLM 抽象层（`services/llm/`）、文件解析（`services/parsing/`）、图表生成（`services/charts.py`）、上传/报表目录的基础读写。
- **边界文件**：
  `app/core/*`、`app/db/*`、`app/services/llm/*`、`app/services/parsing/*`、`app/services/charts.py`；
  前端 `src/api/client.ts`、`src/store/auth.tsx`、`src/router/`、`src/components/Chart.tsx`。
- **规则**：只提供通用能力，不包含任何"任务/成果/评分"等业务语义；不知道上层业务域的存在。
- **对外提供**：`get_db()`、`get_current_user`、`require_role()`、`get_llm()`、`extract_text()`、JWT 签发校验、axios 拦截器与登录态。

### 模块 1：身份与用户域（identity）

- **拥有数据**：`User`（username、hashed_password、full_name、role、email）。
- **后端边界**：`models/user.py`、`schemas/user.py`、`api/v1/auth.py`、`api/v1/users.py`。
- **职责**：注册、登录签发 JWT、当前用户信息、教师对用户的增改、角色判定。
- **对外暴露**：登录态、用户身份与 `role`、用户 id（供其他域外键引用）。
- **依赖**：仅依赖内核（安全、DB）；**不依赖任何其他业务域**（处在最上游）。
- **前端边界**：`login()`、`getMe()`、`listUsers()`、`createUser()` + `store/auth.tsx`。

### 模块 2：实训任务域（training-task）

- **拥有数据**：`TrainingTask`（title、course_name、description、requirements、teacher_id、deadline）。
- **后端边界**：`models/training.py`（仅 Task 部分）、`schemas/training.py`、`api/v1/tasks.py`。
- **职责**：任务的发布、列表、详情、修改、删除；维护"验收要求"文本（它是后续核查/评价的输入来源）。
- **依赖**：身份域（通过 `teacher_id` 引用发布者）、内核。
- **规则**：任务被成果引用，删除任务的约束由本域统一决定；其他域只读 `requirements`，不修改任务。
- **前端边界**：`listTasks()`、`createTask()`，类型 `TrainingTask`。

### 模块 3：成果域（submission）

- **拥有数据**：`Submission`（task_id、student_id、group_name、status、file_names、parsed_content、parse_error）与 `uploads/` 下的物理文件。
- **后端边界**：`models/training.py`（Submission 部分）、`schemas/`（submission 相关）、`api/v1/submissions.py`、`services/structuring.py`。
- **职责**：
  1. 多文件上传（白名单 + 大小限制 + UUID 落盘，规则在内核/规范中）；
  2. 调用内核解析器抽取文本 → 调用 LLM 结构化抽取 → 回写本域的 `parsed_content`；
  3. 维护提交状态机：`uploaded → parsing → parsed → … → failed`。
- **依赖**：任务域（成果必须挂在任务下、读取要求）、身份域（student_id）、内核（parsing、llm、文件存储）。
- **规则**：本域是"成果内容"的唯一写入口；核查域、评价域、报表域都只能读取成果，不得回写 `parsed_content`/状态。
- **前端边界**：`uploadSubmission()`、`listSubmissions()`、`getSubmission()`、`reparseSubmission()`，类型 `Submission`。

### 模块 4：智能核查域（inspection）

- **拥有数据**：`InspectionResult`（submission_id、result_json、overall）。
- **后端边界**：`models/inspection.py`、`api/v1/inspections.py`、`services/inspection.py`。
- **职责**：读取**成果域**的结构化内容与**任务域**的验收要求，调用 LLM 比对，产出三类发现并持久化到自己的表：
  - `deviations` 偏离项（含严重程度）
  - `logic_issues` 逻辑漏洞
  - `missing_steps` 缺失步骤
  - `overall` 总体结论
- **依赖**：成果域（读）、任务域（读要求）、内核（llm、prompts）。
- **规则**：核查结果只写 `InspectionResult`；不修改成果内容与任务要求。重新核查 = 在本域覆盖自己的结果。
- **前端边界**：`inspectSubmission()`、`getInspection()`，类型 `InspectionResult`。

### 模块 5：评价域（evaluation）

- **拥有数据**：`EvaluationRubric`（指标：name、description、weight、可全局可绑定 task）、`Score`（submission_id、rubric_id、ai_score、teacher_score、comment）。
- **后端边界**：`models/evaluation.py`、`schemas/evaluation.py`、`api/v1/evaluations.py`、`services/evaluation.py`。
- **职责**：
  1. 指标（量规）CRUD 与权重管理（教师）；
  2. AI 按指标逐项打分（0–100）并给理由，写入 `Score.ai_score`；
  3. 教师主观调整 `Score.teacher_score/comment`；
  4. 加权汇总：`total = Σ(有效分×权重)/Σ权重`，有效分取教师分（优先）否则 AI 分。
- **依赖**：成果域（读成果来评分）、任务域（指标可绑定任务）、身份域（仅教师可写）、内核（llm）。
- **规则**：评分只落在本域的 `Score`；AI 分与教师分共存、教师分优先这一规则只在本域实现；其他域不计算总分。
- **前端边界**：`listRubrics/createRubric/deleteRubric`、`evaluateSubmission()`、`listScores()`、`adjustScore()`，类型 `Rubric/Score/EvaluationResult`。

### 模块 6：报表域（report）

- **拥有数据**：`Report`（report_type、target、format、file_path、data_json）与 `reports/` 下导出文件。
- **后端边界**：`models/report.py`、`schemas/report.py`、`api/v1/reports.py`、`services/report.py`（+ 复用内核 `charts.py`）。
- **职责**：组装统一"报表载荷"，渲染并导出学生单份报告 / 班级统计，支持 xlsx（openpyxl）与 pdf（reportlab），记录导出历史。
- **依赖**：只读身份、任务、成果、核查、评价各域的数据来聚合；依赖内核（charts、文件存储）。
- **规则**：**只聚合读取、绝不回写任何业务表**；是依赖链的最下游。报表呈现规则（图、模板）只在本域。
- **前端边界**：`exportReport()`、`listReports()`。

## 4. 页面 = 跨域组合视图（再次强调：不按页面拆模块）

| 页面（视图）| 组合了哪些域 | 说明 |
| ---- | ---- | ---- |
| Login | 身份域 | 登录 |
| Dashboard 工作台 | 任务域 + 成果域 + 评价域（只读统计）| 跨域聚合的首页视图，不拥有数据 |
| Tasks 实训任务 | 任务域 | 任务 CRUD |
| Upload 成果上传 | 任务域（读可选任务）+ 成果域（上传/列表）| 一个页面跨两域 |
| SubmissionDetail 成果详情 | 成果域 + **核查域** + **评价域** | 三个 Tab 分别由三个域提供数据与动作，是"页面跨多模块"的典型 |
| Reports 报表导出 | 报表域（+只读任务/成果）| 导出与历史 |

可见 SubmissionDetail 一个页面就横跨三个数据域——这正说明**以页面切模块会切错边界**；正确做法是三个域各自独立，页面只负责编排调用与展示。

## 5. 后端 / 前端边界落地对照

### 5.1 后端（一个域一套垂直切片，统一在 router 聚合）

| 域 | model | schema | service | api/v1 |
| ---- | ---- | ---- | ---- | ---- |
| 身份 | user.py | user.py | ——（安全在内核）| auth.py、users.py |
| 任务 | training.py（Task）| training.py | —— | tasks.py |
| 成果 | training.py（Submission）| training.py/submission | structuring.py | submissions.py |
| 核查 | inspection.py | （result 契约）| inspection.py | inspections.py |
| 评价 | evaluation.py | evaluation.py | evaluation.py | evaluations.py |
| 报表 | report.py | report.py | report.py | reports.py |
| 内核 | db/* | common.py | llm/*、parsing/*、charts.py | deps.py |

### 5.2 前端（按域组织 API 与类型，页面只组合）

- `types/index.ts`：类型按域分组，与后端 Out 模型一一对应。
- `api/index.ts`：用注释分区（认证 / 用户 / 任务 / 成果 / 核查 / 评价 / 报表），每个函数只调用对应域接口。
- `pages/`：允许跨域 import 多个 api 函数，但不在页面内实现任何属于某域的业务规则（加权总分、状态判定等以后端返回为准）。

## 6. 协作规则（跨域调用约定）

1. **读他域**：通过外键 id 调用对方域的查询（service 或关联查询），只读所需字段。
2. **写他域**：禁止。需要对方域产生变化时，调用对方域暴露的 service/接口（例如核查域要推进流程时调用成果域提供的状态更新方法），由 Owner 保证一致性。
3. **外键**：允许持有他域 id（task_id、student_id、submission_id、rubric_id），但不冗余他域名称等可变字段。
4. **避免环依赖**：当前依赖为 身份 → 任务 → 成果 →（核查 / 评价）→ 报表 的有向无环结构；新增功能若会形成环，说明归属判断错误，需重新划分。

## 7. 新功能归属判断示例

| 新需求 | 归属域 | 理由 |
| ---- | ---- | ---- |
| 修改密码、新增班级字段到账号 | 身份域 | 改的是 User |
| 任务增加"评分截止时间" | 任务域 | 改的是 TrainingTask |
| 支持上传 .pptx | 成果域 + 内核 | 落盘/状态在成果域，解析器加在内核 parsing |
| 核查增加"代码规范"检查项 | 核查域 | 产物是 InspectionResult 的新字段/规则 |
| 增加一套默认评价指标 | 评价域 | 拥有 Rubric |
| 教师分增加评语必填校验 | 评价域 | Score 写入规则 |
| 报表新增"班级雷达图模板" | 报表域 | 只改聚合与渲染 |
| 接入文心一言 | 内核（llm）| 新增 Provider，所有业务域零改动 |
| 工作台加一个统计卡片 | 视图层组合 | 只在 Dashboard 读取各域已有统计，不新建模块 |

## 8. 与现有代码的关系

- 本拆分与现有脚手架目录**完全对应**：后端已按 `models / schemas / services / api/v1` 垂直分层、按资源分文件；前端已按 `api / types / pages` 分离数据出口与视图。
- 后续开发只需"按域填充业务"，新增数据先确定 Owner 域，再按《行文规范》第 5.3 节的标准动作落地，不新增平层大目录、不按页面私建数据模块。
