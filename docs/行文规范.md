# 行文规范 —— 大学生软件实训教学 AI 检查评价系统

> 本规范约定本项目脚手架（后端、前端、数据后台）的目录、命名、分层、编码与协作规则。
> 团队所有成员新增、修改代码均须遵守本规范，保证脚手架结构长期一致、可维护。

## 1. 总则

### 1.1 技术栈基线

| 端 | 技术栈 |
| ---- | ---- |
| 后端 | Python 3.11+ / FastAPI / SQLAlchemy 2.0（async）/ Pydantic v2 / PyJWT |
| 前端 | React 18 / Vite 5 / TypeScript 5 / Ant Design 5 / ECharts / Axios |
| 数据后台 | SQLite（开发期，aiosqlite 异步驱动），可无缝切换 PostgreSQL（asyncpg） |
| AI 能力 | LLM Provider 抽象层（本地 Ollama / 云端 OpenAI 兼容）|

未经小组讨论，不得随意更换框架、UI 库或 ORM。

### 1.2 文件与路径红线（重要）

- **所有项目相关文件只能放在 `D:\major\software_engineering\Aiyana` 目录内**，禁止把源码、数据库、上传文件、报表、脚本等放到 C 盘或其他位置。
- 运行期产物的默认目录均在项目内：

  | 产物 | 路径（相对 backend/）|
  | ---- | ---- |
  | SQLite 数据库 | `data/aiyana.db` |
  | 上传的成果文件 | `uploads/` |
  | 导出的报表 | `reports/` |
  | Python 虚拟环境 | `.venv/`（仅本地，不入库）|

- 若安装工具链（Node/Python）时默认缓存落在 C 盘属系统行为，可保留；但**项目自身的一切产出物必须落在 D 盘项目目录**。
- 路径统一使用正斜杠 `/`，Python/TS 代码中禁止硬编码本机绝对路径。

### 1.3 分层总原则

```
前端 pages/components ──HTTP──▶ 后端 api（路由层）
                                  │ 只做：参数校验、鉴权、编排
                                  ▼
                               services（业务层：业务规则、AI 调用、报表）
                                  │
                                  ▼
                               models（数据层：SQLAlchemy 模型 + DB）
```

- 路由层不写业务逻辑，业务层不直接处理 HTTP 细节，模型层不反向依赖路由。
- 前端页面不直接写 `axios/fetch`，一律走 `src/api/` 封装。

## 2. 后端脚手架规范（backend/）

### 2.1 目录职责（已固定，不得随意新增平层目录）

```
backend/app/
├── main.py          # 应用入口：FastAPI 实例、CORS、生命周期建表
├── core/            # 基础设施：config（配置）、security（密码/JWT）
├── db/              # 数据库：base（基类）、session（会话）、init_db（建表+种子）
├── models/          # SQLAlchemy ORM 模型（一张表一个模型类）
├── schemas/         # Pydantic 请求/响应模型（数据契约）
├── api/
│   ├── deps.py      # 公共依赖：get_current_user / require_role / 分页
│   └── v1/          # v1 路由，每个业务域一个文件，并在 router.py 聚合
└── services/        # 业务逻辑
    ├── llm/         # LLM Provider 抽象与实现
    ├── parsing/     # 文件解析（docx/pdf/image + dispatcher）
    └── *.py         # inspection/evaluation/report/charts/structuring
```

### 2.2 命名规范

| 对象 | 规则 | 示例 |
| ---- | ---- | ---- |
| Python 文件/模块 | 全小写 + 下划线 | `training.py`、`inspection.py` |
| ORM 模型类 | 大驼峰单数 | `TrainingTask`、`Submission` |
| Pydantic Schema | 业务名 + `In/Out/Create/Update` 后缀 | `SubmissionOut`、`TaskCreate` |
| 路由文件 | 资源名词单数 | `tasks.py`、`submissions.py` |
| 路由实例 | 统一命名 `router` | `router = APIRouter(prefix=..., tags=[...])` |
| Service 函数 | 动词开头、见名知意 | `run_ai_evaluation()`、`compute_total()` |
| 常量 | 全大写下划线 | `MAX_UPLOAD_SIZE_MB` |

- 数据库表名：小写下划线、**复数**，如 `training_tasks`、`evaluation_rubrics`。
| 布尔字段/变量 | `is_/has_/can_` 前缀 | `is_active` |

### 2.3 API（路由层）规范

1. 统一前缀 `/api/v1`，在 [router.py](../backend/app/api/v1/router.py) 中用 `include_router` 聚合。
2. 遵循 RESTful 风格：

   | 操作 | 方法 + 路径 |
   | ---- | ---- |
   | 列表 | `GET /tasks` |
   | 详情 | `GET /tasks/{id}` |
   | 创建 | `POST /tasks`（201）|
   | 修改 | `PUT /tasks/{id}` |
   | 删除 | `DELETE /tasks/{id}`（204）|

   非 CRUD 动作用子资源或动词，如 `POST /submissions/{id}/inspect`、`POST /submissions/{id}/evaluate`。
3. 每个端点必须声明 `response_model`（无数据返回时返回 204），由 Pydantic 统一序列化，禁止直接返回 ORM 对象而不声明模型。
4. 入参用 Pydantic Body / FastAPI 依赖校验，禁止在函数体内手写类型判断。
5. 鉴权通过依赖注入：登录态用 `get_current_user`，教师专属接口加 `require_role("teacher")`。
6. 路由函数保持"薄"：取参数 → 调 service → 返回结果，**不超过 20 行**，复杂逻辑下沉到 service。

### 2.4 模型与 Schema 规范

1. 所有 ORM 模型继承 `db/base.py` 的 `Base`，统一获得 `id` 与 `created_at/updated_at`（时间戳 Mixin）。
2. 一个文件聚焦一个聚合（如 `training.py` 内含 `TrainingTask`、`Submission`），并在 `models/__init__.py` 统一导出，确保建表时被 metadata 收集。
3. 字段必须写 `mapped_column(...)` 显式声明类型、可空性、默认值、外键；关系用 `relationship`，避免隐式行为。
4. **请求模型与响应模型分离**：`XxxCreate`/`XxxUpdate` 只含可写字段，`XxxOut` 只暴露允许前端看到的字段；密码哈希等敏感字段禁止出现在 Out 模型。
5. 枚举型取值（角色、提交状态）在模型与文档中保持固定取值集合：
   - 角色：`teacher` / `student`
   - 提交状态：`uploaded → parsing → parsed → inspected → evaluated`（异常为 `failed`）。

### 2.5 Service（业务层）规范

1. 业务规则只写在 `services/`，路由和模型都不承载。
2. 所有涉及数据库的 service 函数为 `async def`，通过函数参数接收 `AsyncSession`（由路由依赖传入），不在 service 内部自行 `create_engine`。
3. 调用外部能力（LLM、文件解析）必须容错：外部失败要转成明确的错误信息或可恢复状态（如把解析失败写入 `Submission.parse_error` 并置 `failed`），不能让异常裸抛导致 500。
4. LLM 调用一律走 `services/llm/factory.py` 的 `get_llm()`，禁止业务代码直接 new 某个 Provider；新增模型只加 Provider + factory 分支，业务层零改动。
5. 文件解析一律走 `parsing/dispatcher.py` 分发；新增格式只注册解析器。
6. 公共提示词集中在 `services/llm/prompts.py`，不散落在业务代码里。

### 2.6 配置规范

1. 所有可配置项集中在 `core/config.py` 的 `Settings`，通过环境变量 / `.env` 注入，代码中禁止硬编码密钥、连接串、模型名以外的环境相关值。
2. `.env` 为本地私有配置（含密钥），**严禁提交**；`.env.example` 为模板，必须与配置项保持同步并入库。
3. 新增配置项时同时更新三处：`config.py` 默认值、`.env.example`、《开发文档》第 5 节配置表。
4. `SECRET_KEY` 生产环境必须替换；当前默认值仅限开发。

### 2.7 异常、返回与异步

1. 可预期错误使用 FastAPI 的 `HTTPException(status_code, detail)`，统一状态码：400 参数/业务错误、401 未认证、403 无权限、404 资源不存在。
2. 全程 `async/await`，禁止在异步路径里调用同步阻塞 IO（如同步 requests）；LLM/HTTP 用 `httpx`，DB 用异步会话。
3. 中文注释与 docstring；模块、类、复杂函数必须有一行说明其职责。

## 3. 前端脚手架规范（frontend/）

### 3.1 目录职责

```
frontend/src/
├── main.tsx        # 入口：挂载、ConfigProvider(antd 中文)、AuthProvider
├── App.tsx         # 根组件（RouterProvider）
├── api/            # 唯一的网络出口：client.ts（axios 实例/拦截器）+ index.ts（按域组织的接口）
├── types/          # 全局 TS 类型（与后端 Out 模型对应）
├── store/          # 全局状态（auth.tsx：登录用户 Context）
├── router/         # 路由表 + 登录守卫 RequireAuth
├── layouts/        # 布局（MainLayout：侧边栏/顶栏）
├── components/     # 可复用组件（Chart 等）
└── pages/          # 页面：数据的组合视图，不拥有数据所有权
```

### 3.2 命名规范

| 对象 | 规则 | 示例 |
| ---- | ---- | ---- |
| 组件/页面文件 | 大驼峰 | `SubmissionDetail.tsx`、`Chart.tsx` |
| 普通 ts 文件 | 小驼峰 | `client.ts`、`auth.tsx` |
| 组件名 | 大驼峰 | `function MainLayout()` |
| 变量/函数 | 小驼峰 | `listSubmissions`、`currentUser` |
| 类型/接口 | 大驼峰，接口不加 `I` 前缀 | `TrainingTask`、`Score` |
| 常量 | 全大写下划线 | `TOKEN_KEY` |
| CSS 类名（如需要）| 中划线小写 | `submission-card` |

### 3.3 数据请求规范

1. **只有 `src/api/` 可以发起网络请求**；页面只能调用 `api/index.ts` 导出的函数，禁止在页面里直接 `axios.get` / `fetch`。
2. axios 统一实例在 `client.ts`：配置 `baseURL`、请求头注入 JWT、401 跳转登录、统一错误提示；新增横切逻辑只改这里。
3. 接口函数按业务域分块注释（`// ---- 实训成果 ----`），命名与后端资源对齐：`list/get/create/update/delete + 资源名`，动作型接口用动词（`inspectSubmission`、`evaluateSubmission`）。
4. 所有接口必须声明 TS 返回类型，类型从 `types/index.ts` 导入，与后端 `XxxOut` 字段一一对应；后端字段变更时同步修改。
5. 本地存储只存登录令牌（键名 `aiyana_token`），禁止缓存业务数据/密码。

### 3.4 组件与页面规范

1. 函数组件 + Hooks，禁止 class 组件。
2. 一个页面文件聚焦一个视图；可复用 UI（如图表、表单片段）抽到 `components/`，一次性视图留在页面内。
3. 页面是"数据的组合视图"，可以组合调用多个业务域的接口，但**数据的归属与处理规则以后端域为准**（详见《功能拆分》）。
4. UI 一律使用 Ant Design 组件与其设计变量，不自行引入第二套 UI 库；表格用 `Table`、表单用 `Form`（带 rules 校验）、反馈用 `message/notification`。
5. 样式以 antd 的 `style` 内联/Token 为主，保持与现有页面一致；如新增样式文件，使用与组件同名的模块文件，不写全局污染样式。
6. `null/undefined/空数组` 必须有空状态处理（antd `Empty` 或占位提示），加载中使用 `loading` 态。

### 3.5 状态、路由与类型

1. 全局状态只放真正跨页面共享的内容（当前登录用户），用 React Context（`store/auth.tsx`）；页面私有状态用 `useState/useReducer`，禁止一上来引入 Redux 等重型库。
2. 路由集中在 `router/index.tsx`；需要登录的页面放在 `RequireAuth` 下，角色受限页面在组件内按 `user.role` 控制入口与操作按钮。
3. TypeScript 严格模式：禁止 `any`（确需放宽用 `unknown` 并收窄）；接口返回、props、事件都要标类型。
4. 提交前必须通过 `npm run build`（含 `tsc -b` 类型检查）。

## 4. 数据后台规范（db/ + 文件存储）

### 4.1 数据库与会话

1. 引擎、会话工厂只在 `db/session.py` 创建一次：异步 `create_async_engine` + `async_sessionmaker`；业务代码通过依赖 `get_db()` 获取 `AsyncSession`，用 `async with` 保证关闭。
2. 所有表继承同一个 `Base`（`db/base.py`），模型在 `models/__init__.py` 统一导入，避免建表漏表。
3. 每次请求一个会话，请求结束关闭；service 内通过参数拿到会话，不跨请求共享会话。
4. 写操作遵守"先改对象、最后 `commit` 一次"，异常时 `rollback`；不在多处零散 commit。

### 4.2 表设计规范

1. 主键统一自增整型 `id`；时间字段统一 `created_at`/`updated_at`（由 Mixin 维护）。
2. 外键必须显式声明 `ForeignKey("主表.主键")`，命名 `引用对象_id`（`task_id`、`student_id`、`submission_id`）。
3. 一张表只表达一种数据所有权；跨域只持有外键引用，不把别的域的字段冗余进来（见《功能拆分》）。
4. 大段结构化结果（AI 核查、解析结果）存 JSON 文本字段：`parsed_content`、`result_json`、`data_json`，并在 service 中负责序列化/反序列化。
5. 可空字段显式 `nullable=True`，字符串给出合理长度；状态字段取值与文档枚举一致。
6. 数据库文件 `data/aiyana.db`、`*.db`、`*.sqlite3` 一律忽略，不入库；切换 PostgreSQL 只改 `DATABASE_URL` 并安装 `asyncpg`，模型代码不动。

### 4.3 初始化与种子数据

1. 建表与种子数据只在应用生命周期 `init_db()` 执行（见 `main.py` 的 lifespan）。
2. 种子数据保持最小：仅默认教师/学生账号（`teacher/teacher123`、`student/student123`），供开发联调；生产不得依赖默认账号。
3. 种子写入要幂等：已存在则跳过，避免每次重启重复插入。

### 4.4 文件存储规范

1. 上传根目录 `UPLOAD_DIR=./uploads`，报表根目录 `REPORT_DIR=./reports`，均在项目（D 盘）内，目录不存在时启动/写入前自动创建。
2. 上传保存前：扩展名白名单（docx/pdf/png/jpg 等）+ 单文件大小上限（`MAX_UPLOAD_SIZE_MB=20`）。
3. 落盘文件名一律 **UUID 重命名**，原名只存数据库用于展示，防止路径穿越与重名覆盖。
4. `uploads/`、`reports/` 及 `*.pdf`、`*.xlsx` 产物不入库（见 `.gitignore`）。

### 4.5 数据安全规范

1. 密码只存 pbkdf2 哈希，禁止明文/可逆存储；JWT 由 `core/security.py` 签发与校验。
2. 学生信息、成绩、成果文件均为鉴权后可见；教师专属能力（用户管理、评分、报表）必须 `require_role("teacher")`。
3. `.env`、数据库、上传文件、报表、密钥均不得提交 Git；`.gitignore` 已覆盖，新增敏感产物时同步补充忽略规则。
4. 给 LLM 的成果内容按"数据"而非"指令"处理，Prompt 固定在 `prompts.py` 并要求模型严格依据材料判断，输出做字段归一化与容错。

## 5. Git 与协作规范

### 5.1 必须忽略（已在 .gitignore 配置）

- Python：`.venv/`、`__pycache__/`、`*.pyc`、`.env`
- Node：`node_modules/`、`dist/`、`*.tsbuildinfo`
- 数据与产物：`backend/data/`、`backend/uploads/`、`backend/reports/`、`*.db`、`*.pdf`、`*.xlsx`
- IDE/系统：`.idea/`、`.vscode/`、`.DS_Store`、`Thumbs.db`

判断标准：**可再生的产物与个人/敏感配置不入库；源码、依赖锁文件（package-lock.txt/requirements.txt）、配置模板（.env.example）必须入库**，保证他人 clone 后能按文档跑起来。

### 5.2 提交规范

1. 提交信息使用中文，格式：`<类型>：<简述>`，类型取：
   - `feat` 新功能、`fix` 修复、`docs` 文档、`style` 格式、`refactor` 重构、`test` 测试、`chore` 杂项/脚手架
   - 示例：`feat：成果上传支持多文件`、`fix：修复教师分未覆盖 AI 分的问题`、`docs：补充行文规范`
2. 一次提交只做一件事，提交前自测：后端能加载、前端 `npm run build` 通过。
3. 不提交密钥、数据库、产物文件；发现误提交立即修正而非再提交覆盖。
4. 主分支 `main` 保持可运行状态。

### 5.3 开发流程

1. 新功能按《功能拆分》确认所属数据域，再动手，避免跨域改表、跨层写逻辑。
2. 后端新增一个业务资源的标准动作：`models`（如需新表）→ `schemas` → `services` → `api/v1/xxx.py` → 在 `router.py` 注册 → 更新《开发文档》接口清单。
3. 前端新增一个业务资源的标准动作：`types` 补类型 → `api/index.ts` 补接口 → 页面/组件调用 → 需要则加路由。
4. 完成后：本地验证 → `git add/commit` → `git push` 到 GitHub。
